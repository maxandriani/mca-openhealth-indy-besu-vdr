# Repository guide for coding agents

This repository contains the `indy-besu-vdr` Rust client library for interacting with an Indy2 (Besu/Ethereum) ledger, plus multiple FFI/wrapper packages.

## Architecture (high level)

### Core Rust crate

- **Crate:** `indy-besu-vdr` (see `Cargo.toml`)
- **Entry point / public API:** `src/lib.rs` re-exports most public types and modules.
- **Modules:**
  - `src/client/`: network connectivity, request routing, quorum logic, and the high-level `Client` API.
  - `src/contracts/`: contract-specific builders/parsers grouped by domain (DID, anoncreds, auth, network, etc.).
  - `src/types/`: shared domain types (transactions, signatures, IDs, status, events).
  - `src/error/`: error types and `Result` aliases.
  - `src/utils/`: small shared helpers.

### Optional feature modules

- `basic_signer`: enables `src/signer/` (EcDSA signing helpers).
- `migration`: enables `src/migration/` and related legacy mapping contracts.
- `ledger_test`: enables integration tests that require a running Indy2 ledger.
- `wasm`: enables wasm-friendly dependencies (used by the `wasm/` package).

### FFI / wrappers

- `uniffi/`: UniFFI-based bindings generation for Kotlin/Python/Swift.
- `wasm/`: `wasm-bindgen` / `wasm-pack` bindings for JS/Node/Web.
- `wrappers/python/`: thin Python packaging layer over the UniFFI-generated Python bindings.

## Development workflow

### Build

```sh
cargo build
```

### Test

```sh
cargo test
```

Ledger integration tests (requires a running network):

```sh
RUST_TEST_THREADS=1 cargo test --features "ledger_test"
```

### Formatting

The repo uses Rustfmt with a pinned configuration.

```sh
cargo +nightly fmt
```

## Conventions for changes

- Prefer **small, targeted** changes; avoid broad refactors unless requested.
- Keep the public API stable:
  - Add/adjust exports through `src/lib.rs`.
  - Add new shared structs/enums in `src/types/`.
  - Add contract interactions under the correct `src/contracts/<domain>/` module.
  - Keep error surface centralized in `src/error/`.
- Maintain feature gating:
  - If code is only needed for wrappers (signer/migration/wasm), put it behind the appropriate `Cargo.toml` feature.

## Generated artifacts

Some directories are build outputs and are typically not edited by hand:

- `target/` (Rust build output)
- `wasm/pkg/` (generated by `wasm-pack`)
- UniFFI output directories such as `uniffi/out/` (bindings output)

If a change requires regenerating bindings, prefer updating the source Rust API first, then re-running the generation steps.

## Wrapper workflows (reference)

### UniFFI bindings

From `uniffi/`:

```sh
cargo build --release
cargo run --bin uniffi-bindgen generate \
  --library target/release/libindy_besu_vdr_uniffi.dylib \
  --language <kotlin|python|swift> \
  --out-dir out
```

### WASM bindings

From `wasm/`:

```sh
wasm-pack build --target nodejs
wasm-pack build --target web
```

### Python wrapper packaging

See `wrappers/python/README.md` for the full flow. In short:

1) Generate UniFFI python bindings into `uniffi/out/`.
2) Copy the generated python package and the built dynamic library into `wrappers/python/indy_besu_vdr/`.
3) Build the distribution:

```sh
python3 -m pip install --upgrade build
python3 -m build
```
